



Consider these options for integrating Haskell/Lean in your textbook:

1. **Noweb + Shell Blocks** (your idea): Use `#+BEGIN_SRC haskell :noweb yes` for code display and `#+BEGIN_SRC sh` blocks with `stack ghci` or `lean --run` for execution. Clean separation between presentation and evaluation.

2. **Babel with Wrapper Scripts**: Create wrapper scripts that handle the interpreter session properly, then call them via `:prog` or shell blocks.

3. **Literate Haskell/Lean**: Write entire chapters as literate files (`.lhs`/`.lean`), then extract and compile separately while keeping the org source as documentation.

4. **Export and Compile**: Use babel to export code to temporary files, then compile/run them with shell commands in subsequent blocks.

The noweb + shell approach is likely your cleanest solution within Org mode. It maintains readability while allowing execution demonstrations.

What about using the noweb approach and the "tangling" the source into the haskell or lean source file that the "run" shell blocks can use?


Excellent idea. That's the natural evolution of the Noweb + Shell Blocks approach and is considered a best practice in literate programming with Org.

**How it works:**

1.  **Structure your code blocks** with `:noweb yes` and `:tangle` headers.
2.  **Tangling** (`C-c C-v t`) writes all code to a specified file.
3.  **Shell blocks** then execute the tangled file.

**Example for Haskell:**

```org
#+BEGIN_SRC haskell :noweb yes :tangle /tmp/chapter_code.hs
<<my-function>>
<<main>>
#+END_SRC

#+BEGIN_SRC haskell
<<my-function>>=
greet :: String -> String
greet name = "Hello, " ++ name
=
#+END_SRC

#+BEGIN_SRC haskell
<<main>>=
main :: IO ()
main = putStrLn (greet "World")
=
#+END_SRC

#+BEGIN_SRC sh :results output
cd /tmp && runhaskell chapter_code.hs
#+END_SRC
```

**Benefits of this method:**

*   **Single Source of Truth:** The Org file is the authoritative source. The tangled file is ephemeral (often to `/tmp`).
*   **Clean Execution:** The shell block runs a complete, compiled script, avoiding interpreter state issues.
*   **Professional Workflow:** Directly mirrors how you'd handle a real project: edit source, compile, run.

This combines the best parts of options 1 and 4, making it the most robust and scalable choice for a textbook.

Additional questions: 1) I only need the tangle and noweb declarations where I outline all the function names I will use? 2) How would you suggest handling demonstrations. For example if I write a simple parser library and want several org-blocks where I use functions from the parser library to show how things work. I would not be running the whole source file necessarily, but wanting to load it and demonstrate it.



Excellent questions. Here's how to handle both:

**1. Tangle/Noweb Structure:** Yes, typically you have *one* master block with `:tangle` that references all code sections. This becomes your "main file."

**2. For demonstrations:** Use **session-based evaluation**. Load the tangled module into an interpreter session, then run demonstrations interactively.

**Example Structure:**

```org
#+BEGIN_SRC haskell :noweb yes :tangle /tmp/ParserLib.hs
<<parser-types>>
<<combinators>>
<<example-parsers>>
#+END_SRC

# Individual code sections (no tangle needed here)
#+BEGIN_SRC haskell
<<parser-types>>=
data Parser a = -- ...
=
#+END_SRC

#+BEGIN_SRC haskell
<<combinators>>=
many :: Parser a -> Parser [a]
many p = -- ...
=
#+END_SRC

# DEMONSTRATION BLOCKS (using session)
#+BEGIN_SRC haskell :session :results output
:load /tmp/ParserLib.hs  -- Load your library
let result = parse someExample "input"
print result
#+END_SRC

# Another demonstration later
#+BEGIN_SRC haskell :session :results output
-- Same session maintains loaded state
let another = parse differentExample "test"
print another
#+END_SRC
```

**Key points:**
- Use `:session` to maintain interpreter state across blocks
- First demo block loads the tangled library
- Subsequent blocks reuse the loaded session
- Tangled file serves as the persistent module

This gives you both clean code organization and interactive demonstration capabilities.

This looks great for haskell. Can I do something similar with Lean4? I don't think it has the same :session or interpreter options?


You're right - Lean 4 doesn't have the same interactive session capabilities as Haskell's GHCi. Here's how to adapt the approach for Lean:

**For Lean 4, use a combination of:**

1. **Tangling to build a complete Lean file**
2. **Shell blocks with `lake build` or `lean --run`**
3. **Separate demonstration files for specific examples**

**Example structure:**

```org
#+BEGIN_SRC lean :noweb yes :tangle /tmp/ParserLib.lean
<<parser-types>>
<<combinators>>
<<example-parsers>>
#+END_SRC

# Individual code sections
#+BEGIN_SRC lean
<<parser-types>>=
structure Parser (α : Type) where
  run : String → Option (α × String)
=
#+END_SRC

# Build the library
#+BEGIN_SRC sh :results output
cd /tmp && lake init ParserLib && lake build
#+END_SRC

# For demonstrations, create specific test files
#+BEGIN_SRC lean :noweb yes :tangle /tmp/demo1.lean
import ParserLib

<<demo-setup>>=
def testParser : Parser String := -- ...
=

#main
def main : IO Unit := 
  match testParser.run "input" with
  | some (result, _) => IO.println s!"Result: {result}"
  | none => IO.println "Parse failed"
#+END_SRC

# Run specific demonstration
#+BEGIN_SRC sh :results output
cd /tmp && lean --run demo1.lean
#+END_SRC
```

**Alternative: Use Lake environment + separate demo files**

Create a Lake project and import your tangled library:

```org
# Setup Lake project once
#+BEGIN_SRC sh :results silent
cd /tmp && lake init MyProject && lake update
#+END_SRC

# Demonstration file that imports your library
#+BEGIN_SRC lean :tangle /tmp/MyProject/Demo.lean
import MyProject.ParserLib

-- Your demo code here
#+END_SRC

# Run demonstration
#+BEGIN_SRC sh :results output
cd /tmp/MyProject && lake build && lake exec demo
#+END_SRC
```

While less interactive than Haskell sessions, this maintains clean organization and reproducible demonstrations.
