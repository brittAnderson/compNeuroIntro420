* Some Introductory Comments


Computational modeling of cognition and its implementation in neural systems[fn:1] is not the same as programming.
Though programming often is a prominent part of the practice.
What else could computational modeling be?
What are we losing when we treat our computational model as a programmatic black box.
The plethora of programming languages suggests they are not all equivalent.
Might our choice of programming language based on features actually influence what we can conceive for a computational model?[fn:2]
Why then don't we spend more time considering programming language features when deciding on a programmatic implementation of our computational idea?

Computational modeling is ambiguous in its commitments.
Are we asserting the strong claim that cognition is computation?
This requires knowing what we mean by computation.
Or are we asserting the weaker claim that we can approximate by computational means some cognitive or neural process of which we make no assumptions concerning its computational nature?
What would make an approximation "good enough?"

A model is often used tool for simulation.
Sometimes the code for simulation is offered as the model.
Is that enough?
Should a model be a tool for theory development or assessment?
How do we weigh prediction and explanation when assessing our computational model as tool?

Computational modeling is plural.
It transcends domains: we can be interested in the cognitive or the neural; mind or brain.
We can interest ourselves in different levels abstractly: the computional, algorithmic, and implementation.[fn:3]
We can interest ourselves in different levels concretely: neuron, network, agent, or society.
Levels require choices.
Is our neuron an integrate and fire or Hodgkin-Huxley  or perceptron model?
Is our network a feedforward system fine tuned by backpropagation or an unsupervised autoassociative network ala Hopfield?
Even the abstractions require choices: Turing machines  or lambda calculus or automata?

Computational models are practical.
Different model forms require different tools, practical tools.
Our program may be primarily a labor saving device, but to create a useful mapping between the realms of theories, maths, minds or brains, and code we need to know the write maths. 
We need to be able to read the maths.
We need to be conversant in symbols and notations.
We need to be able to tell a matrix from a vector, to tell imperative code from functional code, and to be able to read and write both equations and programs.

We need to be concerned with all the levels: mind and brain, theory, math, and code.
We can abbreviate these as MTMC: mind → theory → math → code; the arrows indicating  an ordering on our development.
